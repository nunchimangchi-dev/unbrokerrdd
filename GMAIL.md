# Gmail setup for CCPA deletion requests

Strategies 3 and 5 cover 37 targets and never touch a broker's website — they
send a statutory request to an address the broker publishes. Every autonomous
win the browser strategies failed to earn died at a bot defence, and a defence
that blocks a headless browser has no bearing on an email. The blocker here is
entirely on our side.

## What this grant can and cannot do

The scope is **`gmail.compose` and nothing else**. It can create, edit and send
drafts. It **cannot read your mailbox** — not your inbox, not any message.

That restriction has a real cost: the tool cannot read brokers' replies, so
confirming an acknowledgement stays a manual task. Reading the inbox would need
`gmail.readonly`, which grants access to every message in the account. That is
a different thing to hand an automated agent, and it should be your deliberate
decision rather than something that arrives as a convenience. A test asserts
the scope never widens by accident.

## One-time setup — your part

Everything here happens in your Google account; none of it can be done from
this session.

1. Go to <https://console.cloud.google.com/> and create a project (or pick an
   existing one). Name it something like `unbrokerrdd`.
2. **APIs & Services → Library** → search **Gmail API** → **Enable**.
3. **APIs & Services → OAuth consent screen**:
   - User type: **External**
   - Fill in app name, your support email, your developer email
   - Add yourself under **Test users** — this keeps the app in testing mode,
     which is correct here. Do not submit for verification; this is a
     single-user tool.
   - Scopes: you can leave this blank. The scope is requested at runtime.
4. **APIs & Services → Credentials → Create credentials → OAuth client ID**:
   - Application type: **Desktop app**
   - Download the JSON.
5. Save that file as `gmail_credentials.json` in `~/Projects/unbrokerrdd/`.
   It is already gitignored, along with `gmail_token.json`.

## One-time setup — the authorisation

```fish
cd ~/Projects/unbrokerrdd
./databrokergo auth-gmail
```

It prints a URL. Open it, approve, and Google shows you a code. Then:

```fish
./databrokergo auth-gmail --code <the-code>
```

This writes `gmail_token.json` (mode 0600). That file is a bearer credential
for sending mail as you — as sensitive as a password. It is gitignored and
never leaves the machine.

The flow requests offline access and forces the consent screen, because Google
only issues a refresh token on first consent. Without that, the grant expires
in an hour and every later run fails with an opaque 401 long after you have
stopped thinking about it. If Google returns no refresh token, `auth-gmail`
fails loudly rather than saving a credential that cannot renew.

## Using it

```fish
# See exactly what would go out. Touches nothing, needs no credential.
./databrokergo email --broker beenverified --preview

# Create Gmail drafts you can read and send yourself. The default.
./databrokergo email --limit 5

# Actually send. Requires both flags, deliberately.
./databrokergo email --send --i-have-reviewed-these --limit 5
```

**Drafting is the default and sending takes two flags.** These messages go out
in your name, make statements on your behalf, and cannot be recalled. A draft
keeps the irreversible step with the person whose name is on it and costs one
click.

`--preview` needs no credential at all. Nobody should have to authorise an API
to find out what a tool intends to say in their name.

## What the letter claims

The letter is rendered from a fixed template, not generated by a model.
CLAUDE.md originally planned to draft these with Sonnet "so they sound
legitimate and professional" — wrong tool. This is a statutory request whose
force comes from citing the right law and stating the right facts, sent in your
name. It must be identical every time, auditable afterwards, and incapable of
inventing a claim you did not make.

**The letter states residency accurately, per `SUBJECT_STATE`.** The first
version opened with "I am a California-resident-equivalent consumer" for every
recipient regardless of state. There is no such thing as
California-resident-equivalent, and a hedge like that in a request whose whole
force is being a verifiable statutory claim weakens it for a Californian and
misstates it for everyone else.

(For the record: this subject *is* a California resident, so the original text
was clumsy rather than false. The reviewer who flagged it had misread the
state as OH from a placeholder in CLAUDE.md. The fix stands on its own merits
— the letter is now correct for any state — but the alarm was overstated.)

So the opening paragraph is chosen by state:

- A state with a named comprehensive privacy statute in `statutePreambles`
  (CA, VA, CO, CT, UT, TX, OR) gets that statute cited.
- Everywhere else gets a neutral opening that asks for deletion under any law
  that does apply, and under the broker's own published policy where none does.

That is weaker rhetoric and an honest claim. For a letter going out over a real
signature, that is the correct trade. The state list is not legal advice and is
certainly incomplete; adding a state means checking its statute is actually in
effect.

## What gets recorded

`request_sent_at`, `request_method` (`drafted` or `sent`), and `request_ref`
(the Gmail draft or message id, so any claim can be checked against the
account).

`drafted` and `sent` are stored as distinct values and never collapsed. A
drafted request has not reached the broker and must not read as though it had.

**Sending changes no status.** A request leaving the outbox is not a removal.
Only the broker acting on it is, and that is confirmed by hand — which is
exactly the gap the `gmail.compose`-only scope leaves open, on purpose.
